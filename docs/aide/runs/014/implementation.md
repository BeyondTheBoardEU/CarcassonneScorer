# Implementation Report — Item 014
- Agent: aide-implementer
- Status: complete
- Date: 2026-06-21

## Summary
Added the app's state container (`GameProvider` + `useGame()`, React Context + `useReducer`, no new dependency) under `packages/web/src/state/`, holding `{ session: GameSession | null }` and exposing `totals` (always via the core's `computeTotals`), `startGame`, `addScore`, and `newGame`. Updated `App.tsx` to wrap the shell in `GameProvider` and route between minimal `SetupView`/`PlayView` placeholders driven purely by `session === null`. A `initialSession` prop on both `GameProvider` and `App` provides the hydrate seam for tests/Item 019.

## Files changed
- `packages/web/src/state/types.ts` — new: `GameApi` interface (session, totals, startGame, addScore, newGame).
- `packages/web/src/state/context.ts` — new: the `GameContext` object, split into its own non-component module so `GameProvider.tsx` only exports the component (avoids the `react-refresh/only-export-components` lint warning).
- `packages/web/src/state/reducer.ts` — new: `GameState`/`GameAction`/`gameReducer`/`createInitialState`. The reducer only ever assigns a `GameSession` the action already carries (`{ type: "setSession", session }`) or clears it (`{ type: "newGame" }`) — it never calls `createSession`/`addScoreEvent` itself and contains no tally arithmetic.
- `packages/web/src/state/GameProvider.tsx` — new: the provider component. `startGame` calls the core's `createSession` directly (before dispatching) so a thrown `SessionError` propagates synchronously to the caller's `try/catch` instead of aborting React's render phase (see Decisions below). `addScore` calls the core's `addScoreEvent`, supplying `timestamp: Date.now()` and a generated `id` (via `crypto.randomUUID()` with a manual fallback) — the only impure boundary. `totals` is `useMemo`'d from `computeTotals(state.session)`, `{}` when no session.
- `packages/web/src/state/useGame.ts` — new: `useGame()` hook reading `GameContext`; throws a plain `Error` if used outside a `GameProvider`.
- `packages/web/src/state/index.ts` — new: barrel re-exporting `GameProvider`, `useGame`, `GameApi`, `GameProviderProps`, `gameReducer`, `createInitialState`, `GameState`, `GameAction`.
- `packages/web/src/App.tsx` — rewritten: wraps content in `GameProvider` (with a new `initialSession` prop on `AppProps` for the hydrate seam), keeps the Item 011 heading/`core-status` proof, and adds a `GameShell` that renders `SetupView` (session null) or `PlayView` (session present). Both views are explicitly commented as placeholders replaced by Items 015 (setup form), 016 (scoreboard), 017 (score entry), 018 (log). `SetupView` has "start demo game" (2 fixed players) and "start invalid game" (1 player) buttons that call `startGame` inside a try/catch and render a `SessionError`'s message via local `useState` error text (`data-testid="setup-error"`) instead of crashing. `PlayView` lists each player's `name`/`totals[id]`, a `+1` button per player (`addScore`), and a `newGame` button.

## Decisions (for doc-updater)
- **Reducer never calls the core directly; the provider does, before dispatching.** Initially `gameReducer` called `createSession`/`addScoreEvent` itself (closer to the spec's "Proposed shape" sketch with `"start"`/`"addScore"` actions). This broke error surfacing: React runs reducers during the render phase, so a thrown `SessionError` from inside the reducer aborts rendering as an *uncaught* error (visible as a React "above error occurred in <GameProvider>" log and a failed assertion), not as a normal exception at the `dispatch()`/`startGame()` call site. Moving the `createSession`/`addScoreEvent` calls into `startGame`/`addScore` themselves (outside `useReducer`'s reducer function) — dispatching only a pre-built `GameSession` via a single `{ type: "setSession", session }` action — fixes this: a caller's `try { startGame(players) } catch (e) { ... }` now catches `SessionError` normally. The reducer itself is reduced to two trivial cases (`setSession`, `newGame`) with zero core calls and zero arithmetic, which if anything strengthens "no scoring/tally maths in the store." Action/type names therefore differ from the spec's illustrative sketch (`GameAction` is `{ type: "setSession"; session } | { type: "newGame" }` rather than `"start"`/`"addScore"` with raw player/event fields) — the spec explicitly says names may vary; the public `GameApi` shape (`startGame`/`addScore`/`newGame`/`session`/`totals`) matches the spec exactly.
- **Context split into `context.ts`.** `GameContext` lives in its own non-component module (rather than alongside `GameProvider`) purely to satisfy the `react-refresh/only-export-components` ESLint rule already configured for `.tsx` files in this repo — `GameProvider.tsx` now exports only the component (+ its props type, which the rule allows).
- **`addScore` is a no-op (not a throw) when `session` is null.** Calling `addScore` with no game in progress is a programmer error (the placeholder/Items 015-018 should never expose the control without a session), so it is silently ignored rather than throwing — consistent with the spec's framing that only `startGame`'s `SessionError` needs to be surfaced to a caller.
- **`@testing-library/user-event` is not installed** (only `@testing-library/react`/`jest-dom` are devDependencies), so all new tests use `fireEvent.click` instead, consistent with "never add a new runtime or dev dependency."
- **Placeholder views intentionally minimal and inline in `App.tsx`** (not a separate `views/` folder) since the spec scopes this item to "store + shell + routing + placeholders" and Items 015-018 will replace `SetupView`/`PlayView`'s bodies; both are commented with the exact items that replace them.
